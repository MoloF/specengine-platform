# hub-accounts (Phase 7, step 11c): accounts and recovery from a shell on the host

The owner issues and controls accounts, and can always recover access, from a command line in a one-shot container on the host. 3-5 pipeline hours.

- **`spec admin`** (a working name) runs only through a one-shot `admin` compose service, `docker compose run --rm admin spec admin ...`, from the same image, interactive, mounting the login store and the project checkouts. The login store is never mounted into the daemon's container, so the daemon's "no accounts" is kept by isolation, not only by code, and recovery still works with `specengine` down. Its acts: add a user with a role and zones and a one-time enrolment link; list users with state, role and last login; disable; enable; reset (password and passkeys, a new link); an audit log of these acts.
- **No root.** There is no root account and no root password: the right to run it is shell access to the host. It has no HTTP route, no MCP tool and no port; it needs a terminal and refuses without one, as `spec approve` does. It works with the login service down, by writing the login store's files on their volume directly.
- **Recovery.** It therefore recovers the case where every web account is lost, the owner's included. Losing SSH itself is the VPS provider's console, which is the owner's; the README says to keep a second SSH key.
- **A person's state.** Secrets stay in the login store (RM-0064); SpecEngine keeps name, role and zones (`[team]`, RM-0071). ADR-0059 says no account, token or session inside SpecEngine: this item keeps the daemon to that, and the CLI drives the login store from outside the daemon. A change to this supersedes ADR-0059; an owner-confirmed ADR is issued by the slice, not by this item. ADR-0034 says "on any surface", so this slice's ADR names the `spec admin` CLI explicitly. Code tied to the login store's formats lives in the CLI crate, never the core (ADR-0008). `[zones]` is per project and in git while one login store serves the host, so `spec admin add` names a project: two projects, two rows, and a row reaches the hub's clone as a commit through `hub-git` (RM-0051).
- **One spelling.** A hub refuses Unicode format characters (Cf) in a login and no more (`docs/canon/hub.md` "Identity"): Latin look-alikes, NFC against NFD, and invisible marks outside Cf (U+034F, variation selectors, U+3164) stay the door's duty, so `spec admin` refuses them at account creation.
- **Disable.** It takes effect at once on the web. Every request passes forward-auth, so the login door re-reads the person on each request and an existing session dies at its next request. A person's MCP credential is checked at the same door, never in the daemon, and the same act revokes it. An open stream (the UI's events, `/mcp`'s SSE) passed the door once and would outlive both, so streams get a short maximum life and reconnect through the door.
- **MCP credential.** How it is issued depends on RM-0053's by-hand check of a writer's client, the plan's largest unknown; this item issues and revokes whatever that check settles.
- **Verify first**, on the door RM-0064 settles: the one-time enrolment link, and a re-read on every request rather than at an interval.
- **Done.** A person added on the CLI enrols through the link and logs in over TLS; disable cuts them off at once, session included; reset restores a person who lost their passkey; with every web account disabled the CLI still restores one; no route reaches these acts from outside; a CLI call with no terminal is refused.
