# hub-accounts (Phase 7, step 11c-1): accounts and recovery from a shell on the host

The owner issues and controls accounts, and can always recover access, from a command line in a one-shot container on the host that nothing outside reaches. 2.5-3.5 pipeline hours. A hub's stream life split off on 2026-11-03 into RM-0075 `stream-life` (11c-2). Spec: `docs/features/hub-accounts.md`.

- **The root is the host's shell.** There is no root account and no root password: whoever runs `docker compose` on the host is root. No HTTP route, MCP tool or port reaches the acts. Every act that writes needs a terminal and refuses without one, as `spec approve` does. The acts work with `authelia` and `specengine` down, since they write the door's files on their mounts.
- **Design B, the orchestrator's decision of 2026-11-03, the owner's review open.** The acts are the deployment's script: a POSIX `sh` `hub-admin` in `scripts/deploy/admin/`, run as a one-shot `admin` compose service on the pinned Authelia image (whose own CLI hashes and edits passkeys and TOTP), with no network and under a profile, so `up -d` never starts it. Rejected: a `spec admin` in the CLI. It would put account code inside SpecEngine, against ADR-0034's "no token, key, account, session ... on any surface" and ADR-0059's "no account, token, key or session exists inside SpecEngine". It would also reach the daemon's binary, since the daemon links the CLI library. It would need password-hash crates and a YAML writer. And it would still need Authelia's CLI or its SQLite for passkeys and TOTP, where the CLI never links `rusqlite` and SpecEngine's image holds no `authelia` binary. B costs 3.5-5 hours against 5.5-8 for that design.
- **Acts.** Add a person (an ASCII login grammar, a password relayed once), disable, enable, reset (password, passkeys, TOTP), rotate and revoke the MCP secret (one line per person of the proxy's users file, `docs/canon/hub-deploy.md` "Door"), show the second-factor code, list, check, and an act log. The door re-reads a person on every request, so a disable ends a session at its next request. The users folder becomes read-only in `authelia`, so the script is its only writer; that also closes a possible default-user hole in 11b-1's install.
- **A person's state.** Secrets stay in the door. SpecEngine keeps name, role and zones in `[team]` (RM-0071), which the script never writes: it prints the row for a reviewed commit (ADR-0060), and `check` compares a new read-only `spec team` with the door's accounts. No crate holds account code (ADR-0008).
- **Recovery.** With every web account lost, the owner's included, `enable` and `reset` bring one back. Losing SSH itself is the VPS provider's console, which is the owner's; the guide says to keep a second SSH key.
- **ADR `hub-accounts`**, the next free number, owner-confirmed (08's row): it supplements ADR-0034, ADR-0059 and ADR-0067, and closes ADR-0067's cost "kept by hand until RM-0065". It stays a draft in the spec until the owner confirms it.
- **Verify first**, by hand on the pinned images: the spec's VF1-VF3 (the door's CLI, the proxy's reload, a live session's end).
- **Done.** A person added on the host logs in over TLS and enrols with the relayed code; a disable cuts them off at their next request and their AI's next call; a reset restores a person who lost their passkey; with every account disabled the host restores one; no route reaches these acts; an act with no terminal is refused.
