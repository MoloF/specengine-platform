# apply-outputs (Phase 7, step 10a): the index in every apply commit, and a hub's own `PR-` range, no network

Step 10 splits at the first network verb, as step 9 split. This half runs no network verb and makes what a hub commits safe to push. An apply commit, on a terminal and on a hub alike, carries the `index = true` entry's outputs rendered from the committed tree (`HEAD` plus the apply's paths), never the disk walk; a project's own generator commands never run, and a walk gap commits the target alone with a warning. A hub's queue mints `PR-` from a floor stored once in its data directory, `PR-100001` upward. Issues `apply-outputs` (`docs/features/roadmap-items.md`, N12), which unparks RM-0019, and `hub-ids`. Spec: `docs/features/apply-outputs.md`. 2-3 pipeline hours.

- **Why now.** Since `hub-confirm` a create on a hub leaves `index-drift`, an error, so once pushed an `enforce` hook stops a developer's next Markdown commit; and a queue restored from a dump goes on from the same highest number as the one it came from, so a hub and a terminal mint the same `Proposal:` IDs and one's commit on the branch blocks the other's reject.
- **A known limit, stated in canon.** Spec IDs (records, created nodes) are still minted per queue from the root's index: an add/add conflict or `id-taken` after a merge shows a collision, and a person renumbers. The cure waits for RM-0053.
