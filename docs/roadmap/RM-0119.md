# hub-turn-fairness (patch 0.46.1, a fix): a person's page is served before an agent's queued calls

The analyst diagnosed this on 2026-11-14, measuring live on the hosted hub. A person on the page starves while his agent works the same project over `/mcp`. Every call waits in the project's one FIFO turn, and an agent's write costs 2-5 s inside it, so a burst of parallel calls stands ahead of the page. The page also re-queues itself: each `proposal.*` event aborts the Inbox read already waiting, and its replacement joins the back of the line.

The fix comes in two halves:
- **Rust:** a FIFO line per login in front of the turn, for `/mcp` calls alone, so a login has one call at a time in the turn's queue. Nothing is refused, and order within a login is kept.
- **UI:** a live event's re-read never aborts a read in flight. It follows that read once.

The orchestrator's working answers, the owner's review open: the page goes before queued agent calls; with 8 parallel writes every page `/api/` request answers within 10 s; no busy refusal; one line per login. There is no ADR: ADR-0065's "each call in the project's turn" stands.

Spec: `docs/features/hub-turn-fairness.md`. It ships in the patch release 0.46.1 with RM-0114 to RM-0118. The next slices, unspecified: cutting a write's cost, concurrent trusted reads (an ADR), and measuring the memory growth.
