# work-references (Phase 7, pool): photos, sound, models and links attached to work, reaching its agent

From the owner's request of 2026-11-21: a writer attaches a photo of a location, a model or a sound to a task, and it is used later. Under his decision of 2026-11-22, uploads may live on the hub with no off-host copy, a loss risk he accepts (08 s2 Phase 7, "Owner's word, 2026-11-21/22"). It is slice 2 of three, 0.51.0, and comes after RM-0136.

**Decision to come, the next ADR (number 0088, written with the slice's spec).** File bytes go in a BLAKE3-named store inside the data directory, at `<data dir>/blobs/<slug>/`, on a terminal too.
- On a hub the store is its own volume, `specengine-blobs`. It is never in a repository, a dump or an off-host copy, which narrows ADR-0071; the owner's accepted risk is recorded.
- Metadata rows live in the queue (schema 16, table `refs`); format 9 dumps metadata only.
- There is one binary write route, streamed to disk outside the turn; only the row insert takes the turn.
- A file's type is judged by its sniffed bytes. Caps: 256 MiB a file, 10 GiB a project, refused below 5 GiB free.
- Files are served sandboxed.
- Images reach agents as MCP image content, up to a 1 568 px long edge, the browser making a smaller copy at upload. Audio, video, 3D and PDF need a required "what matters here" text. `.blend` files are download-only, with a warning.
- A card's `evidence` stays.

**Surfaces:**
- CLI `spec ref add --on X (FILE | --url U) [--title] [--matters]`, `spec ref list`, `spec ref get RF --out F`, `spec ref delete RF`.
- MCP `list_references {on}`, `get_reference {reference_id}`, `add_reference {on, url, title, matters}` (links only; agents upload nothing).
- HTTP `PUT .../blobs` (`application/octet-stream`, streamed, preflighted, never multipart), `POST .../references`, `GET .../blobs/:b3` (Range), `DELETE .../references/:id`.
- UI: a References part with previews, upload progress and "what matters".
- Uploads are capped at 2 per login and 8 per hub. Delete rights are those of comments.

**Criteria outline, RF1-RF12:**
- types by sniffed bytes alone: SVG, HTML, XML and archives refused, HTML renamed `.png` refused;
- the caps, the quota and the free-space floor apply mid-stream: 413, and the temp file removed;
- resident memory during a 200 MiB upload stays within a fixed buffer;
- a blob's file name equals its BLAKE3, and dedup keeps one file;
- served with `nosniff`, `CSP: sandbox`, and `Content-Disposition: attachment` except for raster images, audio and video; Range works;
- "what matters" is required for audio, video, 3D and PDF;
- cheap metadata, else `null`;
- `get_reference` returns an image or its downscaled copy;
- delete rights as CM6; GC in the turn;
- soak "RF": 2 uploaders of 200 MiB, 10 Range readers and the CM writers, with the page p95 unharmed;
- compose and volume tests in `deploy.rs`;
- owner's gates: a 100 MiB upload through Traefik, and an image delivered to Claude Code.

**Hub:** the new volume is mounted at `/data/specengine/blobs` on `specengine` only, and the Dockerfile creates the mount point owned by uid 10001. "Restore" and "Upgrade" never remove it. The accepted loss risk is recorded in `hub-ops.md` "Known limits".
