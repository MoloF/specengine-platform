# hub-ops (Phase 7, step 11b-2): off-host dumps, restore, upgrade, health and turning on `--push`

Split from RM-0064 on 2026-11-03 (the orchestrator's decision, the owner's review open): what keeps a running hub alive once 11b-1's files serve it. Where off-host dumps go (Q5 of `hub-deploy`), the orchestrator's working answer of 2026-11-04, the owner's review open: restic, to any backend restic supports, set in `.env`; recovery must never depend on an outside account for login. 1-1.5 pipeline hours, all in `scripts/deploy/` and its README.

- **Dumps.** Every 15 minutes, off the host: the queue (`spec export state`, one per served project), the login store, where the deploy key lives (never the key in clear), the proxy's MCP users file and `hub-admin`'s act log, taken under that script's lock (RM-0065), because losing the VPS must not force everyone to re-enrol. The login store's dump is encrypted: it holds password hashes and passkey records. To settle here: Authelia's storage encryption key must itself be restorable, or its database restores to nothing; Authelia's SQLite needs an online backup, never a file copy under a running door; `export state` keeps no retention, so the job prunes.
- **Restore.** Into an empty queue (`spec import-state` under `docker compose exec -it`) and an empty door volume, from the dumps alone, ending with `hub-admin list` and, by hand, the acts its log records after the dump. Without `--push`, restored `applied_commit` values point at commits that died with the host: the guide says so, and turning `--push` on closes it.
- **Upgrade.** `SPECENGINE_VERSION` raised in `.env`, then pull and `up -d`, a dump first, because queue migrations run forward only. Before the hub's first spec-ID mint (a record or a create), every `spec` that writes to the repository, each developer's and the host's, runs `v0.29.1` or later (`docs/canon/spec-ids.md` "Older binaries"); the guide's "Limits" says so.
- **Health.** A hub answers a loopback probe with the fence's 403, which means alive (`docs/canon/hub.md` "Known limits"); from outside, the door answering `/` means alive. No forged identity and no new route. The image holds no HTTP client, so the container probe's tool is this step's choice.
- **Turning on `--push`.** After the gate (step 11b-3): a write deploy key for the one repository and a pinned `known_hosts` (`docs/canon/hub-git.md` "Credentials"), `SPECENGINE_PUSH=1`. The hub pushes to the game's main branch, the one its checkout tracks, and merges, never rebases (RM-0051, the owner's decision of 2026-11-03), so a merge commit lands there whenever the hub and a developer have diverged: a linear-history protection on that branch is lifted for the hub's deploy key, and the guide says so.
- **Done.** On the gate's host: a dump runs on schedule and lands off the host; a restore onto a fresh VM brings back the queue and the accounts; an upgrade keeps both; the health check turns a stopped daemon unhealthy; with `--push` on, a confirm's commit reaches the remote.

Since 2026-11-04 it comes after RM-0073 `spec-ids`, the owner's order for the hub's release (08 s2 Phase 7, "Release scope").
