# write-cost (patch 0.47.1): a write's check pays for what it touches, and the confirm's POST reuses its GET's findings

On the hosted hub (2 vCPU, 1 841 documents), a question's confirm GET holds the turn 3.2-3.3 s and its POST 4.4-4.6 s. Three things make it slow:
- every write reads and checks the whole tree twice;
- every write re-parses every file the call has just decoded;
- the POST repeats the GET's rehearsal.

The owner gave three words on 2026-11-15:
- "do all the points, 1, 2, 3 at once";
- "include b in the release; step c, can also be done right away";
- "make sure not to break the project ... a team of up to 10 people in parallel".

**Ships:**
- (b), ADR-0083: a write's findings take the files as the call's walk indexed them, trusting stat keys as reads do. Only the changed file and the affected set are read, checked against their rows.
- The as-is memo C and the findings memo D, keyed by a computed walk-state digest. D's key also holds the login, and both live inside the project's turn with a 32 MiB budget.
- The incremental check E, over the exact affected set from the index's dependency tables.
- The ID preview and holder lookup, as queries.
- Five git spawn cuts.
- Five line fields: ` check_ms= index_ms= git_ms= git= write_ms=`.
- A 10-login concurrency test.
- The hub entrypoint's `SPECENGINE_SLOW_MS`, so the gate can be read from the daemon's lines.
- Test hygiene: the wall-clock tests in `crates/specengine-core/tests/cost.rs` and `crates/specengine-code/tests/hash_levels_depth.rs` made relative.

Every layer equals the whole disk check byte for byte, order included.

**Deferred:** (c), in-process git reads, which buys 0.01-0.07 s per call against a C library. This is the working answer; the owner's review is open.

**The gate:** GET ≤ 1 000 ms, POST ≤ 2 000 ms, MCP `propose_change` ≤ 1 500 ms. The POST's ≈1 s waits for a durability slice measured by `write_ms`. No schema, format or `INDEX_FORMAT` step.
