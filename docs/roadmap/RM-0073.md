# spec-ids (Phase 7): spec IDs that a hub and a terminal never mint twice

Shipped 2026-11-04 (`docs/features/spec-ids.md`, `docs/canon/spec-ids.md`, ADR-0070 `spec-ids`), the first item of release `v3`. The cure (S1-S7), the settlements (D1-D12), the ADR and the changes of review iteration 2 are the orchestrator's working answers and await the owner's review.

- A data directory holding `proposal-floor`, a hub's, mints every number-shape spec ID, a record or a created node, from 100001; any other mints below it. Each counts only its own side's numbers, in the index and the queue, so a hub's and a terminal's IDs never meet at a merge.
- Propose refuses a created ID on the other side, exit 1, naming the next free one; apply never judges a side (ADR-0012). `id-width` passes a hub's number. No format changes; plugin 0.29.1, the hub's release tag `v0.29.1`.
- Known limits of `v3`: two terminals still collide, and an older `spec` mints in the hub's range, so every writer upgrades before the hub's first mint (RM-0074 "Upgrade").
