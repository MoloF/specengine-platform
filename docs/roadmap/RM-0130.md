# hub-backups (Phase 7, pool): the hub's off-host backups run, and the door's dump stops failing

These are findings from the orchestrator's upgrade of the hosted hub to 0.47.2 on 2026-11-20. The owner's standing rule makes every stability finding a task with its evidence. Two of the three dump sidecars (`hub-ops.md` "Dumps") are not doing their job. As a result, **no off-host snapshot exists**, and **the door's users, passkeys and TOTP are not dumped at all**.

**Evidence** (`docker compose logs`, 2026-11-20):
- `backup` restarts in a loop. Every round logs `hub-ops: upload <t>: restic_env: no RESTIC_REPOSITORY line: name the repository`. A bad setting is exit 2, which ends the loop (`hub-ops.md` "Dumps", "Exits"), and `restart: unless-stopped` starts it again.
- `dump-door` fails every 15-minute round with `hub-ops: door <t>: skipped: hub-admin: the door's passkey export failed: Error: failed to load configuration from file path(/config/configuration.yml) source: stat /config/configuration.yml: no such file or directory`, the error twice in one line. The service in `scripts/deploy/docker-compose.yml` mounts no door configuration, so `authelia storage user webauthn export` (in `hub-admin dump`) cannot load one.
- `dump-queue` works: two projects were dumped. A pre-upgrade copy of the queue sits on the host in `~/hub-snapshots/20261120-before-0.47.2/`, as before every earlier upgrade.

**The fix asks for:**
1. **`dump-door`** gets the configuration its export needs:
   - either the door's `configuration.yml` mounted read-only where the CLI looks;
   - or `hub-admin dump` passing `--config`;
   - with whatever settings that configuration reads from secrets or the environment, so a round touches no network.

   **Test:** a `dump-door` round on the compose stack (`docker compose run --rm dump-door door once`, with a door holding one user and one passkey) exits 0, and writes `users.yml`, `webauthn.yml` and the TOTP export. The static compose test (`tests/deploy.rs`) pins the mount or the flag. **Mutation:** the mount removed turns it red.
2. **`backup`** with a missing or bad `restic_env` stays up, unhealthy, and logs one line per round naming the missing key: never a restart loop. This changes "a loop ends on 2" for `upload`, so `hub-ops.md` "Exits" changes in the same change.

   **Test:** the round with no `RESTIC_REPOSITORY` exits nothing over three slots and logs three lines. **Mutation:** exit 2 restored turns it red.
3. **The owner's step, when he turns backups on**, never automated (`hub-ops.md` "Restic"). His word of 2026-11-20: off-host backups stay off for now ("not required, don't worry about it, let it stay off"). Until then `backup` waits unconfigured, one line per round:
   - choose the repository and its credentials;
   - write `secrets/restic_env` and `secrets/restic_password`;
   - run `docker compose run --rm backup init` once;
   - read `docker compose run --rm backup snapshots` for both tags after a round.

**Done when**, on the live hub:
- `dump-door` dumps every round;
- `backup` stays up and unhealthy, with one line per round and no restart loop.

When the owner turns backups on, `backup` reports `fresh` with a `queue` and a `door` snapshot under 35 minutes old, and a restore drill (`hub-ops.md` "Restore") on a scratch host reads both back. It ships after 0.48.0, as 0.48.1.

Plan: 08 s2 Phase 7, "Owner's word, 2026-11-19", the paragraph "Ops findings, 2026-11-20".
