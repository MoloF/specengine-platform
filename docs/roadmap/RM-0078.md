# edge-table (Phase 7, step 12c): resolved edges kept in the index, incrementally

Split from RM-0054 on 2026-11-03 (the orchestrator's decision, awaiting the owner's review). Today every read resolves every link (`SpecGraph::build`). This stores the resolved edges in the index and keeps them incrementally, under the store's property that an update equals a rebuild, row for row; `INDEX_FORMAT` 16. Reads do not change yet (RM-0079). 2-3 pipeline hours.

- **E1.** The table is a pure function of the stored rows, the `[ids]` fingerprint and the `[paths]` keys resolution reads.
- **E2.** Stored edges equal core's resolution: one core produces them, and SQL holds no second rule set.
- **E3.** No read orders by rowid. **E4.** Nothing computed per read is stored. `parent:` is resolved at parse time.
- **Risks.** Two resolvers drifting (E2). A missing dependency key leaves an edge stale: fallback candidates, feature-scoped references, `aliases_from`, anchors and relative links each need one.
- **Done.** After any sequence of edits the incremental table equals a rebuild's (the canonical dump), and its edges equal core's resolution on every fixture and on RM-0077's corpus.
