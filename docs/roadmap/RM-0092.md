# card-tasks (Phase 7, v4 step 3b): the `T-` tasks behind a card

The spec is `docs/features/card-tasks.md`, with ADR-0075 `card-task-link` (`docs/canon/card-tasks.md` "The rule"). This follows the owner's decision 3 of 2026-11-08: an agent task shows inside its card. 4-6 pipeline hours.

- **The link.** A card-to-`T-` link lives on the card row, behind queue schema step 9 -> 10 and backup format 4, which still imports 3. `spec card edit C --task T…` replaces the list and `-` clears it. Each entry is an existing task, listed once, at most 32, and one edit is one `card.edited`.
- **The read.** `show` and `get_card` serve each linked task's `{id, status, title, stale}`, read at request time. The card modal and page get a Tasks block; MCP `edit_card {task}`, plugin 0.32.0.
- **What it decides.** Nothing. No gate, transition, approve, claim or accept reads a link, and a task's state refuses no card.
- **Local only.** The owner's Q2 of 2026-11-09: a hub holds no `T-` task, so a hub card shows linked IDs without state.
- **Risks.** The schema step reaches the gate. An older `spec` behind the hook gives no verdict until spec and the plugin reinstall from one commit, and older importers refuse format 4; the spec gives the owner's upgrade steps. `T-` IDs are minted per queue. The canon index shard splits at ship (`docs/index-canon-card.md`).
