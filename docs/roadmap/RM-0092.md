# card-tasks (Phase 7, v4 step 3b): the `T-` tasks behind a card

Shipped 2026-11-10, uncut (`docs/features/card-tasks.md`; ADR-0075 `card-task-link`; `docs/canon/card-tasks.md`). This follows the owner's decision 3 of 2026-11-08: an agent's task shows inside its card. 4-6 pipeline hours.

- **The link.** A card's list of `T-` IDs lives on its own row, behind queue schema step 9 -> 10 and backup format 4, which still imports 3. `spec card edit C --task T…` replaces the list and `-` clears it. Each entry is an existing task, listed once, at most 32, and one edit is one `card.edited`.
- **The read.** `show`, `get_card` and the daemon serve each task's `{id, status, title, stale}`, read now; one that cannot be read here is `null` with a note. The card modal and page show a Tasks block, re-read on `task.*`. MCP `edit_card {task}`; plugin 0.32.0.
- **What it decides.** Nothing: no gate, transition, approve, claim or accept reads a link.
- **Local only** (the owner's Q2 of 2026-11-09): a hub checks and reads no task and shows linked IDs without state.
- **Upgrade.** Older binaries refuse a stepped queue, and the hook gives no verdict until `spec` and the plugin reinstall from one commit: the owner's steps are in `docs/canon/card-tasks.md` "Known limits".
