# hub-deploy (Phase 7, step 11b-1): Docker compose with Traefik and Authelia, from a clean VPS to a hub

`scripts/deploy/` and the `.github/workflows/image.yml` workflow take an operator from a clean Linux VPS with Docker to a running hub in one sitting: `Dockerfile`, `docker-compose.yml` with `specengine`, `traefik` and the login door, `.env.example` (domains, ACME email and CA, image version, the push opt-in), Traefik's and Authelia's config, an entrypoint, a clone script, a step-by-step README. `scripts/` is already the rust-developer's (ADR-0029), so the folder needs only a `roots` entry. A first real project stays small until `scale-reads` (RM-0054). 3-4 pipeline hours; task spec `docs/features/hub-deploy.md`.

Split on 2026-11-03 (the orchestrator's decision, the owner's review open): dumps, restore, upgrade, health and the `--push` steps are 11b-2 `hub-ops` (RM-0074), which waits for the owner's answer on the off-host destination; the checks on a clean VM are the gate, step 11b-3 (08 s2), the owner's session, which `--push` and real people wait for. The board snapshot (RM-0052) is no prerequisite: nothing here reads one.

- **Documents.** A host folder holds each project's checkout, bind-mounted; a separate named volume holds the data directory (SQLite index and queue), on a local disk, never a network share. A guide and a clone script bring a project over: a clone with every blob, never shallow or blob-filtered, because an apply renders the index from the committed tree and must not fetch (`GIT_NO_LAZY_FETCH=1`, RM-0072), checked out sparse to the paths `spec sparse-set` prints (`hub-git`); then `spec export state` and `spec import-state`, whose consent is a terminal, so under an interactive `docker compose exec`. No path is rewritten (ADR-0032): an open proposal arrives an orphan, only rejectable, so the guide decides them before the dump.
- **The push.** The hub's `--push` (`docs/canon/hub-git.md`) is turned on only after the gate, since a forged `Remote-User` would reach the shared remote; the image carries git 2.38 or later (`merge-tree --write-tree`), and the hub's checkout has its upstream, its committer identity and its whole history.
- **Git LFS.** The image ships no git-lfs, and LFS content in the cone is unsupported: a smudge filter run by the hub's fast-forward could reach the network, which `GIT_NO_LAZY_FETCH` does not cover (`hub-git`, RM-0051).
- **The bind, settled.** `network_mode: "service:traefik"` keeps the daemon's 127.0.0.1 bind and ADR-0034's letter, so no bind ADR, and publishes no daemon port. Traefik reads a file provider, never the Docker socket, because the host is agent-free. Restarting `traefik` alone through compose restarts `specengine` too (`depends_on` with `restart: true`); a Traefik crash restarted by the engine leaves `specengine` with no network until `docker compose up -d`, a known limit the gate tries.
- **Identity, settled.** Authelia is the self-hosted login door, because recovery from the server must never depend on an outside account; oauth2-proxy over an outside provider is rejected as the primary door. Its access-control `resources` rules match request paths by regular expression, which is how `hub-confirm`'s step-up on confirm routes is expressed (checked against its docs on 2026-10-31). Traefik removes a client's copy only of a header listed in `authResponseHeaders`, so `Remote-User` is listed there and only the forward-auth response sets it. Passkey login, and deleting a lost passkey from a command line, are tried at the gate; if either fails, TOTP stays the second factor and the guide names the fallback.
- **The host.** It still runs no agent and nothing else untrusted (ADR-0059): the compose file is the whole host, and the daemon's port is never published.
- **What `hub-identity` stands on.** The daemon cannot tell the proxy's header from any process reaching its socket, so this step guarantees `docs/canon/hub.md#trust`: the port unpublished and nothing but the proxy in that network namespace; `Remote-User` set by the proxy alone on every router reaching the daemon, no router or `bypass` rule without the door; `passHostHeader` left on, so the daemon sees the public `Host`; no agent on the host. The daemon starts with `--public-origin` naming the final domain.
- **What `hub-confirm` stands on.** The daemon cannot see a step-up: it trusts one header (ADR-0059), and a marker header would be a second one to scrub and prove a router matched, not a factor. So this step guarantees a fifth item of `docs/canon/hub.md#trust`: a session with one factor reaches none of the four routes taking a `Consent` (a stage takes none), by a step-up rule on exactly this regex:

  ```text
  ^/api/projects/[^/]+/(proposals/[^/]+/confirm|cards/[^/]+/(accept|clear)|trace/clear)$
  ```

  The rule lives in `docs/canon/hub.md#trust`, item 5, which the test reads, and the routes in the daemon, and a forgotten rule passes silently, so `the_step_up_regex_is_the_confirm_class` (`docs/features/hub-confirm.md` B11) pins the regex to the fence, and this step adds the half that test cannot reach: a test that the rule in `scripts/deploy/` holds the same bytes. The daemon refuses any query on the four, and a raw `#`, which `http::Uri` drops before the fence, reaches it encoded by the proxy (from memory), so a handler never answers a form a `$`-anchored rule missed (`docs/canon/hub.md` "Known limits"). The confirm read shares the path, so a one-factor session learns at dialog open. Tried at the gate: that the door's path rule sees the query, that its step-up is a session level (a second factor on the session, not a click a person's), and that a one-factor `fetch` meets a redirect, status 0, nothing confirmed.
- **What `hub-mcp` stands on.** The daemon cannot tell an MCP client's `Remote-User` from a browser's, so this step guarantees item 6 of `docs/canon/hub-mcp.md#trust`. Two door paths: the routers matching `^/mcp/[^/]+$` take the MCP credential, and every other router takes the browser session alone. The credential, for now (the orchestrator's decision, the owner's review open): a per-person random secret checked by Traefik's `basicAuth` on those routers alone, `headerField: Remote-User`, its user name the person's Authelia login byte for byte, never an email, a UUID or a `client_credentials` subject, which would split one person in two; Claude Code sends it as a static header. Room stays for an OAuth router on the same matcher later. `Authorization` stays in place on every other router, so the daemon's refusal outside `/mcp` is a second line. A `scripts/deploy/` test pins the rule's bytes to the canon's, as item 5's. Until the claude.ai half of the client check (`docs/canon/hub-mcp.md` "Client check"), run at the gate, AI on a hub means Claude Code; writers without it use the web UI.
- **A restored dump's `Author.login`.** Bringing a project over runs `spec import-state` of a dump, and the queue's row decoder checks an author's `role`, `model` and `run` but not `login` (store `queue.rs`), which `provenance()` writes raw into `Proposed-by:`: a crafted dump with an LF in a login could add trailer lines. This step checks `login` on decode with the hub's own login rule (core `hub_login_problem`), never the ASCII rule of the other three, which would refuse valid logins (from `hub-confirm`; `docs/canon/hub-confirm.md` "Known limits").
- **The login's sibling subdomain.** The login door sits on a sibling subdomain of the hub, so its landing arrives as a `same-site` navigation, which the hub admits on `GET /` alone and refuses everywhere else. Tried at the gate in a browser, as is what the door answers to a JSON request when a session has expired: a redirect fails as status 0 in the page.
- **A body timeout.** The daemon sets no deadline on a request body. `[team]` is judged before a body and again once it is in, so a slow body keeps no power, but a login can still hold a connection and a body read open: the proxy's entry point sets an explicit read timeout, above the longest expected call.
- **Hardening headers.** `nosniff` and COOP on every router to the daemon, at Traefik (`docs/canon/hub.md` "Known limits").
- **A launcher on the host.** `spec serve --root <served>` attaches to a hub: it exits 0 with `already running` and a loopback URL that answers 403, and another root is told to stop the hub. `daemon.json` keeps its five keys and this fails closed, so the README names it.
- **Secrets.** The git deploy key the hub pushes with is a Docker secret granted to `specengine` alone, never in the image or `.env.example`; the door's secrets are Authelia's alone.
- **Image.** The repository is public: `image.yml` builds on a version tag, for linux/amd64 and linux/arm64 on native runners, and publishes to GitHub Container Registry, so publishing happens only when the owner pushes a tag; the first tag is `v` + the plugin's version, 0.29.0 (ADR-0015, one version). The image carries `spec`, `specengine-http` and `git`, a second channel beside ADR-0015's `cargo install`. No Rust toolchain or `rust-analyzer`: code binding on the host is out of this item. The server only pulls: the compose file pins a version from `.env`, never `latest`, and with no registry the fallback is `docker save` piped over SSH to `docker load`. The VPS does not build: a Rust and UI build is not a job for 2 vCPU and 4 GB. Third-party images and actions are pinned exactly, their versions pending the owner.
- **Domain.** Passkeys and any OAuth callback bind to it, so it should be final before people enrol; a free dynamic-DNS or IP-based name is for a dry run only, under Let's Encrypt's staging CA. Recommended: a domain for the hub alone, the hub and the door on two of its subdomains. The owner buys it.
- **Sizing.** At least 2 vCPU, 4 GB of memory, 40-80 GB of local SSD, from a measurement on 2026-10-31 on a laptop, not a VPS: a 5 050-document synthetic corpus, index 20 MB, daemon 99 MB resident plus 35-50 MB per request, reads serialised per project.
- **Done (11b-1).** The task spec's criteria, checked on a laptop with no image build and no network, and its CI-only checks on the first tag: the files pin every trust item a test can reach.
- **The gate, step 11b-3.** On a clean VM or the VPS, by the owner: `.env` filled in and `docker compose up -d` serve the UI over valid TLS; the daemon's port is unreachable from outside; a client's forged `Remote-User` is dropped on every router, with and without a session; a person lands on the board after login in a real browser; a session with one factor reaches none of the four step-up routes, and a second factor opens them; the MCP credential opens `/mcp` and stops at the door on every other router; restarting the stack, or `traefik` alone, keeps the hub serving and the queue; a restore from a dump brings back the queue and the accounts (with RM-0074). Only people can do: buying the domain, DNS, the VPS itself.
