# per-event-reads (pool): delivery and the other reads repeated on each proposal event read every state

Found 2026-11-20 by RM-0134's analysis (`docs/features/mixed-load-memory.md`), outside its fix by decision: not measured there.

**Evidence:**
- On each proposal event the UI reads again the inbox, the proposal, the card on screen, the tasks and `spec delivery` (`ui/src/api/queries.ts`, the proposal-event branch).
- `spec delivery` lists every state of every repository (CLI `delivery.rs:423`, `list_readable` with no state filter). Its cost grows with the queue's whole history, applied and rejected included, not with what is pending, so RM-0134's state prefilter does not reach it. RM-0134's row-by-row decode drops the raw copy, but every decoded `Proposal` is still kept.
- RM-0134's M soak has no Delivery or card reader, so nothing has measured these reads.

**The task asks for:**
- which per-event reads read every state, named by file:line;
- a write soak variant with those readers beside the writers over a long history (`WRITE_SOAK_PENDING` and a few thousand decided rows), two runs of 300 s under both judges of `docs/canon/soak-runs.md`, and a per-read peak curve as `rm0134_inbox_peak_by_pending`;
- a targeted fix only if a run is red, accepted by a clean re-run, with identical answers behind an oracle.

**Why should, not must:** nothing is measured red. The reads grow with history only while a person keeps Delivery or a card open during proposal events. If a soak breaches a budget, it becomes a must under ADR-0086. Nothing blocks on it (ADR-0012).
