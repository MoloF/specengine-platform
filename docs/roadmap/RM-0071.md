# hub-team (Phase 7, step 9a): accept, clear and stages under a `[team]` login, no spec file changed

Per project, `[team.<login>]` in `specengine.toml` says who may act on a hub. The fence sorts its routes into classes; accept, clear, group clear, stages and round answers open to the logins `[team]` names, and no spec file changes: a terminal on the host confirms until RM-0050. An identity not in `[team]` keeps reads and the five plain writes. Issues `hub-team`. Spec: `docs/features/hub-team.md`. 2.5-3.5 pipeline hours.

- **`[team]`.** `name`, `role`, `zones`, `email`. `zones` name that file's `[zones]`, so `spec check` can judge them, and a role change is a reviewed commit (owner's decision 1); a host file would be a second truth outside git. The reader is a core change (`project_toml.rs` `RawFile` denies unknown keys, so the new table makes older binaries refuse the file).
- **Accept and clear take the login (criterion).** `accept_card`, `clear_card` and `clear_group` do not call `hub::acting`, and `CardAcceptBody` defaults to `local`, so listing them alone would let any login accept as anyone. The step runs `acting` in each.
- **What a hub holds meanwhile.** No route proposes until `hub-mcp` (RM-0053), so a hub's queue holds only departing accepts' discrepancies, what the operator raises on the host, and imported orphans, which only reject (RM-0064 "Documents"). This step delivers a mechanism and its proofs.
- **`by`** stays literal: a move reading `[team]` would let a bad `[team]` stop a plain write, so a project lists logins.
- **A suspect mark** stays as built, no consent added: a retarget or a cancel of an open card is recorded under the login, and refusing them because a mark stands would be a discrepancy blocking work (ADR-0012).
