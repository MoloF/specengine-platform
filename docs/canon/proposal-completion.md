# Proposal completion and reject

How a proposal closes without a new apply: its own commit completes it, or `spec reject` closes it unapplied (ADR-0004, ADR-0005, ADR-0032). Consent, the questions and the apply steps named here: `proposal-apply.md`; a record's, a create's: `decision-record.md`, `proposal-create-apply.md`; revisions: `proposal-revisions.md` "Completion and reject"; a drift item's: `proposal-drift.md` "Approve". Code: CLI `apply.rs` (reject, completion; `reject_follow_up`, `drift_carried`), `preflight.rs` (the trailer lookup, `TrailerCommit.unread`), `follow_up.rs`; store `WorktreeGit::{branch_commits_with_trailer, name_status}`, `SqliteQueue::reject_with_task`; core `task` (`FollowUp`, `follow_up_title`, `follow_up_goal`, `FOLLOW_UP_REASON_MAX`).

## Completion

A proposal's own commit on its branch completes it, no new commit: an interrupted apply, a cherry-pick, a split. **Where**: the recorded worktree when it is a directory of the recorded repository; else the current repository when it is the recorded one (worktree removed); else refused, naming why (the worktree gone and its repository not the current one, no longer a git worktree, another repository's). **Which**: commits with `Proposal: <id>` in `base_commit..refs/heads/<branch>`, newest first; the base commit not in the repository (pruned after a rebase): the branch's whole history. A gone branch fails the lookup: ``the branch `t1` no longer exists; recreate it at its last commit (`git branch t1 <commit>`), then `spec approve PR` or `spec reject PR` ``; base gone too, adding that its base commit <sha> is not in the repository. **Completes**: one parent, only the target's path changed (or with `spec.lock`, `Lock-mode: editorial`), its span equal to step 5's result, raised or not, on the first parent's blob (what an apply wrote on top of it) or on its own blob (the new text; a split or cherry-picked merge), each blob raw (`cat-file blob`) parsed under the `<root_rel>/specengine.toml` of that commit's tree, else the one read now (the recorded root's; the current project's for a current-repository read). Else why: `changes a, b`, `has N parents`, `does not carry the proposal's text`, `cannot be read: …`. Each kind's judge (`trailer_commits`): a deciding kind's `record_commit`, a new file's `file_commit`, a drift item's `drift_commit` (one parent, only `<root_rel>/spec.lock` changed and present, `Lock: <target_id>`, `Lock-mode: accept|editorial`; checked before `trailer_commit`, which would parse the lock as Markdown), else `trailer_commit`.

Looked up by approve before step 2 and at step 5, by review, by reject before and after its prompt. Completing (a task's snapshot refreshed as at step 10): `approved -> applied`, no prompt; `open -> applied` after the `complete` question, the identity of where it was looked up (none -> exit 2, logged as step 7); note `` `PR` completed by its commit <sha> on `<branch>`; no new commit ``; writes the queue and the data directory's index only (failed reindex: a `warning:`). A failed lookup is a note for approve and review (appended to an exit-2 reason at steps 2-6) and refuses reject. Hint (steps 5, 10, reject; `completes_when`, by kind): ``a commit on `<branch>` with the trailer `Proposal: PR`, one parent, changing only `<path>` to the proposal's text completes it (`spec approve PR`)``; a drift item's names the trailers `Proposal: PR` and `Lock: <ID>` and `spec.lock`. A drift item's completion writes no index entry.

## Reject

`reject(…, &RejectRequest {id, reason?, …}, consent)`: `open` or `approved` only (a deciding kind: `decision-record.md` "Reject"; else exit 1 `` `PR` is applied: only an open or approved proposal is rejected (commit <sha>) ``), never with a `Proposal:` commit on its branch (a `drift` item: one completing it, below), checked before and after the prompt; refused: nothing written, no event:

- its completing commit -> exit 1 `` `PR` has its commit <sha> on `<branch>`: a proposal whose commit is in history is never rejected; `spec approve PR` completes it ``;
- another, not a drift item's -> the newest named, ` (<k> older one(s) too)`, why it does not complete, the hint;
- a failed lookup -> exit 1 `` cannot tell whether `PR` has its commit in history: <why, with the way out> ``.

Then `reject_from` on the state read (changed since -> exit 1); `decision_note` the reason, `proposal.rejected` (`reason`; `staged_at` confirming a stage; `task` only with a follow-up). `decided_by`: the committer where the history was read, else the current repository's; none -> exit 2.

**A drift item** (`drift_carried`, plain or followed up): its `Proposal:` commits judged by `drift_commit` ("Completion"). A completing one refuses as above; one git cannot read (`TrailerCommit.unread`) refuses `` cannot tell whether `PR` has its commit in history: the commit <sha> on `<branch>` cannot be read: <error> ``; any other (no `Lock-mode`, `regen`, other paths, `spec.lock` deleted) never blocks: one note naming the newest, `` the commit <sha> on `<branch>` carries `Proposal: PR`<more> but does not complete it (<why>); rejected all the same `` (`<more>` ` (<k> older one(s) too)`, k > 0), above the question (as `noted`'s), on stderr and in `--json` `notes`; the lookup after `y` adds its note only when it differs.

**Follow-up** (`spec reject PR --reason T --follow-up code|spec`, `reject_follow_up`; ADR-0045): a drift item's reject also making a `draft` task (`tasks.md`; `spec task approve` makes it `ready`, ADR-0012). After the item is read: another kind -> exit 2 `--follow-up: only a drift item has a follow-up` (another value: clap's exit 2); an orphan -> exit 1 `--follow-up: the repository <git_common_dir> of PR no longer exists; reject without it`, a recorded worktree gone `… the worktree <w> of PR …`; the recorded root's config unreadable or its slug another -> exit 2 `--follow-up: <error>`; its `[ids]` taking `T` -> exit 2 (core `task_prefix_clash`). Then reject's checks and lookup, the identity, and the node resolved now at the recorded root (`recorded_project`, CLI `propose.rs` `resolved_at`): no node has its canonical ID (an alias too) and every walked file was read and parsed -> exit 1 `--follow-up: R-12 names no node now; reject without it`; not one node (several holders, or any walked file unread, unparsed or not UTF-8, `nodes_known`) -> exit 1 `--follow-up: <resolver's reason>; reject without it`, for an unparsed holder ``--follow-up: `R-12` resolves to no ID and no alias; reject without it``; the recorded index not refreshed -> exit 2; its revision unreadable -> exit 1 `--follow-up: the revision of R-12 in <path> cannot be read now; reject without it`. The one prompt: the note above if any, `draft task: <title>`, `goal:`, each goal line indented two spaces, then the question ending ` and make a draft task (code)? [y/N]`, escaped whole. After `y`, `reject_with_task`, one `Immediate` transaction: `reject_from`'s compare-and-set and the task (the node's canonical ID, author `human`); `proposal.rejected` gains `task`, then `task.created`; another kind or no target: `Invalid`, neither written. stdout `rejected PR`; note `created T-0003 (draft) for PR: spec task approve T-0003 makes it ready`.

Title (`TITLE_MAX` 256 B, cut with `…`) and goal (lines; `GOAL_MAX` 4 096 B), stack-neutral: `code` `Bring the code bound to R-12 in line with its spec (PR)`, ``R-12 rev 3 (<path>) is the spec: change the bound code below to match it and set its markers to @3; the owner then locks them (`spec lock accept R-12`, or the approve of a new drift item).``; `spec` `Propose a spec edit of R-12 matching its bound code (PR)`, `The bound code below is right: propose an edit of R-12 rev 3 (<path>) describing it; once applied, set its markers to the new revision, and the owner accepts the lock.`; then `Owner's reason: <reason>` (line breaks as spaces, other controls kept, escaped on output; 1 021 B + `…` at most, `FOLLOW_UP_REASON_MAX`), the stored rows as `spec review` prints them, each indented two spaces, while the goal fits, then `<k> more row(s): spec review PR`.

**Orphans** (`proposal-queue.md` "Place, IDs, repositories"): rejected `open` or `approved`, with the note `` `PR` belongs to the repository <dir>, which no longer exists ``. The lookup runs in the current repository on the branch of its name: skipped when neither branch nor base commit is there (another repository); the branch alone missing refuses with the way out ending ``then `spec reject PR` ``; a commit found refuses, suffixed ``; it was recorded in the repository <dir>, now gone or moved: move the repository back to <dir> (`git worktree repair`), then `spec approve PR` `` (`<dir>`: the recorded common dir).

## Known limits

None blocks; the apply's own: `proposal-apply.md` "Known limits".

- A reject running while a live apply commits between reject's second check and its write leaves it rejected with its commit in history (the apply's step 10 exits 1, `rejected`): needs a cross-process lock.
- An end-of-line or clean/smudge filter on spec files (`core.autocrlf`, `eol=crlf`): completion compares raw blobs with worktree bytes: an apply interrupted at step 10 is neither completed nor rejected (later: `cat-file --filters`).
- The trailer names no project: with several SpecEngine roots in a repository, or a reset data directory, another proposal's same-ID commit on the branch blocks reject; with the base pruned the whole-branch read finds older ones too; approve refuses only when that commit applied the text.
- A reverted apply commit: approve refused at step 5, reject refused; way out: a completing commit (the hint).
- A drift item is rejected while a commit naming it but not completing it sits in history (the note).
- A follow-up refused for an unread file names no file: the index records an unreadable file as unparsed (`CheckFile::unreadable`), and step 1 cannot tell the two apart.
- A follow-up whose node sits in a directory that cannot be listed, or under a non-UTF-8 name, reads `names no node now`: the walk never reaches it; the refresh warns on stderr (``cannot list `<dir>`: …``, ``<n> directory or `.md` names skipped: not UTF-8``).
- A follow-up whose holder's front-matter does not read (`FrontmatterYaml`, `FrontmatterUnclosed`, `FrontmatterNotMapping`) counts the holder as read: a gone document-level target there reads `names no node now` (later: `nodes_known` also requires no `front_matter_failure`).
- An orphan whose branch was renamed and base pruned is rejected without the lookup, even with its commit on the renamed branch.
- An orphan rejected from a clone that never had its branch refuses (branch missing): `git branch <branch> HEAD`, `spec reject`, delete the branch.
- A transient failure of only step 5's lookup is dropped (no note); consent still precedes the write.
