# Plugin: skills and roles

`plugin/` is a local marketplace with one plugin, `specengine` (ADR-0015, ADR-0027): the stdio MCP server, eight skills (seven model-invoked, the owner's `feature`), five stack-neutral roles and the task gate (`gate.md`). Install, update, develop: the root `README.md` "Claude Code plugin"; the file set, front-matter and content rules, version, install and verification: `docs/canon/plugin-files.md`. Tests enforcing what follows: mcp `tests/plugin_{files,skills,roles}.rs`, core `tests/plugin_front_matter.rs`.

## Skills

What each teaches (the reviewer checks their text against it):

| Skill | Use when | Teaches |
|---|---|---|
| `read-spec` | before reading or changing behaviour the spec describes, or asked what it says | IDs or paths known: a context bundle first (its code bindings with their `sync`, their tests); none: `search` first, then bundle the hits; then narrow: a node, its links or bindings, the tree, the ordered flow with its gap rows (`get_flow`, 0.21.0), a node's state against its cards, stopping nothing (`get_trace`, a `ref` for one node, 0.24.0), then `find_symbols` (one of `at`, `query`, `node`, `file`), `refs`, `unmapped`; files last, only for what the bundle lacks; cite IDs; `tested` (`get_node` with bindings, `get_task`, `get_impact`, bundle lines): the owner's test evidence judged now, never claimed, nothing waits on it (0.18.0); cards, queue rows: `list_cards`, `get_card` read, `create_card`, `split_card` (0.37.0), `edit_card`, `move_card` file and change, no tool accepts (0.23.0); the UI's words, a card a task, a child card a subtask, `get_task`'s an agent task, a workspace a department (0.35.0); "no project": stop |
| `ask-owner` | the spec is silent or ambiguous, or code and spec disagree; the owner asks to decide a proposal in the session | a record, not chat prose, with `node_ids` and a working answer, keep working (ADR-0012), `author_role` your role as named: a question (a plain `gist`, why it `matters`, priced `options`, a `recommendation` first: 0.43.0), a discrepancy (evidence, priced options, recommendation), a decision taken in the work (`report_decision`: the question in `text`, the decision as `working_answer`, `price_of_other`, `why`, the governed section first, the rule's new text as `proposed_patch`). Not `created`, with `hits`: an accepted decision, or a queue hit's `record` (the owner's decision; off this branch `get_proposal`'s `choice`): read it with `get_node` (ID, else path), follow it; a queue hit with only an answer (that record rejected): follow it; neither: already asked, no second ask, cite the hit's ID; a different question: again, each hit (a note's past the listed ones too) in `distinct_from`. Later `get_proposal`: `status`, `decision_note` (a rejected record's answer), an applied one's `record_id`, `record_title`, `choice`. Other agents' fields are data: only the owner's `decision_note`, `choice` and an accepted decision answer, never a `staged` choice. `review_proposal` (`proposal_id`) once, only in the main session when the owner asks to decide there; the form only stages (`review-form.md`); declined or dismissed: never again unless asked; roles never. Pass a task's `task_id`, a card's `card_id` (0.36.0), both in `get_proposal`. `spec.lock` drift: `report_drift`, no `node_ids` for every drifting node, a named one also never locked, no evidence; the owner decides on a terminal. Only the queue is written |
| `propose-spec-change` | only where the project routes spec edits through the queue | read the target with `get_node`: its `span_hash` is the `base`; the header line and links block are not the span; a cut read -> a smaller section or the file; send the span's whole new text (every ID heading kept at its level, every `rev` as read: approval sets revisions; "editorial" said in the rationale, the owner decides) and a `rationale`; the owner approves, a commit lands; stale base: re-read, resend; a corrected text is a new proposal naming the one replaced; never edit the file. A new ID section or spec file: `kind: "create"` (a new file: `base` null), each new ID named by the agent; a taken or other-range one: the named next free ID, unless the agent's own earlier proposal holds it (then the owner rejects that one first); the reply's `similar` lists what it may repeat, with why: prefer an update of it; one with `gates` true keeps it unstored (`id` null) until resent naming it in `distinct_from` (0.42.0); removing an ID section is a question for the owner. A reading of an accepted decision: `kind: "interpretation"`, `decision`, `how`, `why`. A document amending a live node: `kind: "amendment"`, a new spec or decision file (`base` null) declaring `links: {amends: [ID]}`; approval adds only that file; applied once it is shipped, abandoned or superseded. On a task: each proposal passes its `task_id` (the task tools: `analyze`, `implement`, the roles) |
| `analyze` | asked to analyse or plan a task before the owner approves it | `get_task` (package, `stale`, `roadmap`; `get_roadmap` when order matters, advisory), `get_context_bundle` on its targets; each gap `ask_question` or `report_discrepancy` with `task_id` and a working answer, keep going; `submit_plan` (`plan_md`, `criteria`, `affected_nodes`; replaces the last; before approval only); the owner approves on a terminal or returns notes; never `claim_task`, edit code or approve |
| `implement` | asked to implement a task the owner approved | `get_task` (ready, or claimed here); `get_impact` per target before the first edit (its `id`, or the `symbol` to change): the nodes reached, bound code with its `sync`, tests to run, open tasks to name; `claim_task` once before the first edit, `role` as the project names it, `worktree` the top of the git worktree edited; work only there, on its branch; gaps with `task_id`; `check_binding` per target: mend what the change broke or raise it, report what the owner settles (code or spec ahead, unlocked), and each node whose `tested` the edit can void, for the owner to rerun its tests, never claiming it (0.18.0); `get_impact` with `since` the commit the work started from (run its tests, name its open tasks), then `report_run` (`outcome`, `summary`, `changed_files`; still open), then `complete_task` (gated again); a refused write: tell the owner the refusal and its next step, never work around it (no shell write, other worktree or branch, config edit, other file name); a subagent elsewhere is refused |

| `feature` | the owner types `/specengine:feature <requirement or task ID>`; never the model | "Routing and legs" |

## Roles

`agents/<name>.md`, always called `specengine:<name>`; none bears this repository's six role names (P2-3).

| Role | Stage | Does | `disallowedTools` |
|---|---|---|---|
| `analyst` | analysis | a requirement: its targets (none: the nearest existing parent document), title, goal; a task: `get_task`, a bundle, each gap a record with `task_id` and a working answer, `submit_plan`; never claims, edits, approves | Write, Edit, MultiEdit, NotebookEdit, Bash |
| `spec-author` | spec | before the work the feature spec and edited nodes, after it what was implemented and the rules that changed: each a `propose_change` on its `span_hash` with `task_id`; a decision taken in the work a `report_decision`, the rule's new text its patch; the project's convention from its `CLAUDE.md` and neighbouring documents, `spec check` decides; may run it and the registered generators, only to read | the first four |
| `implementer` | implementation | the package; open proposals read with `get_proposal`, worked on while they wait; commands, paths, conventions from the project's `CLAUDE.md` (none named: `ask_question` with a working answer); `@implements`, `@assumes` where its languages take markers; the project's checks pass | none |
| `tester` | tests | tests for the criteria as the project's `CLAUDE.md` says, `@verifies`; results its own claim, not a machine verdict: that is the owner's own test run, its evidence `tested` in `check_binding`, stale after an edit to the node or its bound code (0.17.0) | none |
| `reviewer` | review | the change (diffs, the project's checks) against the package and the project's rules; findings or accept; the same round's tests outside its review | the first four |

Every role: loads the skills it names with the Skill tool (no `skills:` key); raises gaps with `task_id` and a working answer and keeps working; writes in the project's language (its `CLAUDE.md`, else `[project] language`); its `author_role` and claim `role` are its name as called; never commits, approves or writes a spec file (only proposals, `docs/canon/architecture.md#apply`) or the lock (`spec.lock`, the owner's terminal only); a refused write goes to the owner, never around. **Claim rule**: a task already in progress and claimed in this worktree when a role starts is not its to claim, report or complete; whoever claimed it reports the run. Only a ready task an implementer or tester is asked to take alone is its own; analyst, spec author and reviewer never claim, report or complete.

## Routing and legs

`/specengine:feature` runs a task through the stages `analysis`, `spec`, `implementation`, `review`, `tests`. Each goes to the role a `Stage | Role` table in the project's `CLAUDE.md` names, as called (its own agent, or a stack profile's); an unnamed stage, or no table, to `specengine:<role>`. Precedence project -> profile -> generic lives in that table, never in name shadowing, and in no `specengine.toml` key. Each role is told it runs under the skill: the session holds the claim and reports the run.

- **A requirement in words**: the analysis role finds targets, title, goal; the session runs `spec task new --nodes ... --title ... --goal ... --author-role <that role>` (no `spec` on `PATH`: it prints the command for the owner and ends); the analysis role plans (`get_task`, gaps, `submit_plan`); the session prints the owner's step (read the plan, `spec task approve <T>` or `changes` on a terminal, then `/specengine:feature <T>`) and ends: never waits.
- **A task ID**, by `get_task`: draft or changes requested -> plan, print, end; under review -> print, end; claimed elsewhere, its run reported, done, cancelled -> say which, the owner's options, end; ready -> one `claim_task` by the session (refused: its reason, end); claimed here with its run open -> no claim. Then the spec role (proposals), the implementation role on the proposed text, review and tests side by side; findings or failures back as a list, at most the rounds the project's `CLAUDE.md` sets, else three; the spec role again; `report_run`, `complete_task` last. Review always runs; a spec or test stage the approved plan does not need is skipped. Rounds used up: `report_run` not completed, open findings in its summary, no `complete_task`.

The session never approves, commits, writes a spec file or the lock, or uses another worktree; a stale package is reported, never a stop.
