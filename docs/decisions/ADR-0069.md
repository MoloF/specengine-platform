# ADR-0069

**Decision.** Accepted by the orchestrator in the owner's absence, awaiting the owner's review. A read's freshness step reads a file only when its stat key (size, mtime and ctime in ns, inode, device) moved or was taken within 2 s of the file's last change; no opt-out, `spec index --full` repairs, the code index stays on content. On a hub, only reads trust: they answer from the index its confirms and merges update in the turn, replaying the last walk's warnings, and walk after start, a doubt or 5 minutes; a printed file is checked against its row. A route or tool that writes or authorizes a write walks, as do trace data wherever shown and an unknown route or tool.

**Why.** At 100 000 nodes the step was the read: 376 ms, 349 of it hashing files to learn that nothing changed. A hub's tree has no editor of its own.

**Cost.** On a hub a hand edit on the host is unseen by trusting reads until a reconcile (300 s) or `spec index`, while writes, trace and printed bytes (T5) see the disk; no other process raises the dirty mark. A same-size edit moving neither mtime nor ctime waits for a key move or `--full`.
