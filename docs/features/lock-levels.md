# lock-levels (5b-1a): spec.lock format 2, its writers and readers

## Why

Format 1 kept one v2 `ast_hash` per item and only its file's blob for a `module` or `ron` binding: declared levels were dead, and any edit of a RON file or a module's file was drift for everything bound in it (05:137). Verify can judge by levels only once the lock holds them; the bytes freeze at the first format-2 lock (ADR-0050). 5b-1 split (Q22): this slice (format 2, its writers and readers, verify judging as v2 did, `lock_code`, both goldens, the `lock.rs` pin); 5b-2 `lock-rebase.md` right after, closing the window (a format-1 lock stops verify and the writers until rebased; none exists: Q23); then 5b-1b `lock-levels-verify.md` (verify by levels), the carry-overs' XS slice, 5c.

## Description and interactions

As built, in canon: `docs/canon/spec-lock.md` (the file, "Entry" with the reader and format 1, "Lockability", regen), `spec-lock-accept.md` ("Steps" 5-6, "Exits"), `spec-verify.md` ("States", "Cascade", cause (6), "Known limits"), `proposal-drift-item.md` "The item", `proposal-revisions.md` "Editorial approve", `code-hash.md`, `code-hash-ron.md`, `architecture-code.md` "As built". **The owner** meets a format-1 lock, or one of another `code_recipe`, as exit 2 naming `spec lock rebase`; `spec check`, `spec bump` and a review's vouching count keep reading it. **An agent** sees no new state, detail or JSON key; an item edit v2 saw but `sig` and `body` do not (N5's, N6's reorders, a CRLF checkout's CR: `code-hash.md` "Levels") now reads `ok`; `report_drift`'s evidence carries the new `lock_code` and an item's `code` per changed level. Nothing is blocked (ADR-0012): the gate and plain `spec check` never read the lock. Store, MCP, HTTP, UI, plugin and eval code unchanged; no new crate or dependency.
